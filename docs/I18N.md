# Interface languages and profile appearance

The dropdown beside the theme button selects English (`en`), French (`fr`),
German (`de`) or European Portuguese (`pt-PT`). Short codes keep the sidebar
compact; each option has its native language name as its accessible label.
English is the default and fallback for unknown messages. Everything needed for
translation is shipped with the application; no translation service or internet
connection is used.

Changing language saves the active profile and reloads the interface at its
current address. Pending integration and panel edits are saved first. Ordinary
navigation still retains the caller and board views. Theme-only changes apply
without reloading. Other open Oche tabs follow the active profile's appearance
through the existing settings polling.

Translation covers Oche's controls, navigation, headings, help text, status
descriptions, validation feedback and game controls. Player, profile and device
names, addresses, identifiers and configuration values are preserved. External
Autodarts Play pages, custom panels, terminal output and raw device diagnostics
keep their own language. Unrecognized diagnostic messages retain their English
source rather than being guessed or altered.

## Profile storage

`data/core/profiles.json` now includes an `appearances` entry for every profile,
containing `theme` and `language`. This is the authoritative appearance store.
The active settings are mirrored to `data/core/ui.json` for the existing UI
settings service. Both files stay outside application releases.

Existing profiles without appearances inherit the installation's existing UI
settings when first loaded. Cloning a profile copies appearance; a new blank
profile starts with dark theme and English. Selecting, importing or deleting an
active profile applies the remaining or newly selected profile's appearance.
Profile export includes the optional `appearance` field; older version-1 exports
without it inherit the current appearance when imported.

Profile changes and appearance saves share the runtime lock. A failed save rolls
back the profile change. Browser writes can include `profile_id` in `PATCH
/api/ui`; stale requests from another profile are rejected instead of changing
the newly selected profile. `GET /api/ui` reports the active profile ID alongside
theme and language.

## Adding or editing messages

The catalogues live in `app/static/locales/`. `en.json` is the English message
inventory; `fr.json`, `de.json` and `pt-PT.json` use identical message keys. Keep
code, protocol values and message IDs in English.

In Jinja templates, use `{{ _("Start game") }}`. For variable content, use named
parameters, such as `{{ _("Show {name} in the sidebar", name=_(label)) }}`. Jinja
escapes translated output normally.

Browser modules import `tr` from `app/static/js/i18n.mjs`; ordinary scripts use
the early-loaded global `tr`. Use `tr("Player {0}", {0: number})` for interpolation.
Keep placeholders unchanged in every language and assign translated text through
the existing text/attribute controls. Do not pass saved user names through the
translator. The current catalogue is safely embedded into the HTML before scripts
run, including the standalone setup-terminal page.

Run these checks after editing:

```sh
uv run python scripts/check_translations.py
uv run pytest -q
node --test tests/test_frontend.mjs tests/test_integrations_frontend.mjs
```

The catalogue checker verifies message coverage, nonempty translations and exact
interpolation tokens. Python tests cover page rendering and profile migration,
switching, import/export, persistence and rollback. JavaScript tests cover message
formatting, English fallback, saving before reload and delayed profile responses.
Visual acceptance and native-speaker review remain separate from these checks.
